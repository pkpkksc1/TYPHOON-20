좋아. 지금까지 만든 내용을 기준으로 **“이 대시보드는 무슨 데이터를 쓰고, 어떤 기준으로 위험도를 판단하며, 각 API가 어디에 쓰이는가”**를 한 문서처럼 정리해볼게. 지금 올린 README는 아직 **JMA Step 1 기준**이고, 거점도 MNL이 빠진 5개로 적혀 있어서 현재 프로젝트 상태와는 차이가 있어. 

# SBLC 태풍 물류 대시보드 운영 기준

## 1. 대시보드 목적

중국 쑤저우 물류 운영 시 태풍 발생에 따른 영향을 한 화면에서 판단하기 위한 대시보드다.

핵심 판단 대상은 **20호 태풍 GAENARI의 현재 상태, 5일 예상 이동경로, 물류 거점 위험도, 주요 물류 노선 위험도**다.

단순히 태풍 중심과의 거리만 보는 방식이 아니라, **태풍의 강풍반경 + 거점까지 거리 + 현지 강수/풍속/돌풍**을 같이 본다.

---

# 2. 사용 중인 기상기관 / API

| 구분   | 기관/API                  | 현재 상태 | 대시보드에서 사용하는 정보                   | 역할                  |
| ---- | ----------------------- | ----- | -------------------------------- | ------------------- |
| 🇯🇵 | **JMA 일본기상청**           | ✅ 운영  | 현재 위치, 예상경로, 중심기압, 최대풍속, 이동방향·속도 | **기본 태풍 경로**        |
| 🇰🇷 | **KMA 한국기상청**           | ✅ 운영  | 예상경로                             | JMA 경로와 예보 편차 확인    |
| 🇨🇳 | **CMA 중국기상국**           | ✅ 운영  | 현재 위치, 중심기압, 최대풍속, 강풍반경          | 중국 측 현재 상태 참고       |
| 🇺🇸 | **JTWC**                | ✅ 운영  | 예상경로, 34/50/64kt 강풍반경            | **거점·노선 위험도 계산 핵심** |
| 🌦️  | **WeatherAPI**          | ✅ 운영  | 강수량, 평균풍속, 돌풍 및 72시간 예보          | 각 거점 현지 기상 위험       |

JMA는 공식 XML의 `台風解析・予報情報（５日予報）`를 사용하며 VPTW60~65 계열을 수집한다. 고빈도 feed와 장기 feed를 함께 읽고, 고빈도 feed에 데이터가 없으면 장기 feed를 fallback으로 사용하는 구조다. 현재 README 기준 JMA 수집 주기는 **30분마다** 설정되어 있다.

# 3. 왜 기상기관을 4개나 쓰는가

**4개 기관의 숫자를 평균 내서 하나의 가상 태풍 경로를 만드는 방식은 아니다.**

기관마다 가장 유용한 정보를 나눠서 사용한다.

**JMA**를 기본 경로로 삼고, **KMA**는 같은 미래 시각의 예상 태풍 중심 위치가 JMA와 얼마나 다른지를 확인한다. **CMA**는 중국 측에서 발표하는 현재 태풍 상태를 참고하고, **JTWC**의 강풍반경은 실제 물류 거점이 강풍 영향권에 들어가는지를 계산하는 데 사용한다.

따라서 최종 물류 위험도는 **각 기관의 예보를 억지로 섞은 평균값**이 아니라, 서로 다른 데이터의 장점을 조합한 결과다.

---

# 4. JMA ↔ KMA의 km 차이는 무엇인가

대시보드에 표시되는:

**평균 위치 차이 138 km**
**최대 위치 차이 214 km**

같은 값은 태풍 크기나 강풍반경 차이가 아니다.

기준은:

> **같은 예보 시각의 JMA 예상 태풍 중심좌표와 KMA 예상 태풍 중심좌표 사이 거리**

이다.

예를 들어 48시간 뒤 JMA가 예상한 중심과 KMA가 예상한 중심이 120km 떨어져 있고, 72시간 뒤에는 180km 떨어져 있다면 이런 시점별 거리의 **평균값이 평균 위치 차이**, 가장 많이 벌어진 시점의 거리가 **최대 위치 차이**다.

따라서 이 값은 **“기관별 예상경로가 얼마나 벌어져 있는가”**를 보는 참고정보다.

`차이 있음 / 없음` 같은 애매한 문구는 제거하고 실제 km 값을 보여주는 방향으로 정리했다.

---

# 5. 현재 물류 거점

현재 대시보드 기준 거점은 **6개**다.

| 코드     | 거점            |
| ------ | ------------- |
| SUZHOU | 쑤저우           |
| PVG    | 푸동 국제공항       |
| ICN    | 인천 국제공항       |
| MNL    | 마닐라 국제공항      |
| HAN    | 하노이 노이바이 국제공항 |
| CRK    | 클락 국제공항       |

초기 README에는 SUZHOU/PVG/ICN/CRK/HAN 5개만 있었지만 현재는 **MNL을 추가해 6개로 확대**했다. 

각 거점에서는 현재 **태풍 최접근 거리, 접근/이탈 추세, 현재 강수, 풍속, 돌풍** 등을 표시한다.

# 6. 주요 물류 노선

현재 대표 노선은 다음 **5개**를 운영한다.

| 노선              | 용도    |
| --------------- | ----- |
| 쑤저우 → PVG → 한국  | 중국 수출 |
| 쑤저우 → PVG → 하노이 | 중국 수출 |
| 쑤저우 → PVG → 클락  | 중국 수출 |
| 쑤저우 → PVG → 마닐라 | 중국 수출 |
| 한국 → PVG        | WF수입  |

노선 위험도는 해당 노선에 포함된 물류거점들의 위험도를 바탕으로 판단한다.

예를 들어 `쑤저우 → PVG → 마닐라`라면 **SUZHOU / PVG / MNL**의 상태를 함께 본다.

# 7. 태풍 거리 판단 기준

처음에는 단순하게:

> “태풍 중심에서 400km 또는 500km 이내면 위험”

같은 기준을 검토했지만, 태풍마다 크기가 다르기 때문에 사용하지 않기로 했다.

현재 핵심 기준은 **태풍 중심거리와 JTWC 강풍반경의 관계**다.

즉:

**태풍 중심까지 400km**라는 숫자 자체보다
**현재 거점이 실제 강풍 영향권에서 얼마나 떨어져 있는가**가 중요하다.

JTWC에서 가져오는 대표적인 강풍반경은:

| 원본   | 의미           | 대시보드 해석     |
| ---- | ------------ | ----------- |
| 34kt | 약 17.5m/s 이상 | **강풍 영향권**  |
| 50kt | 약 25.7m/s 이상 | 강한 강풍 영역    |
| 64kt | 약 32.9m/s 이상 | 매우 강한 바람 영역 |

화면에서는 일반 사용자가 `34kt`를 바로 이해하기 어려우므로 **“강풍 영향권”**이라는 쉬운 표현을 우선 사용한다.

---

# 8. 강풍 영향권 주의 기준

현재 적용해둔 주요 기준 중 하나가:

**CMA_CAUTION_MULTIPLIER = 1.5**

다.

기본 개념은 예를 들어 해당 방향의 34kt 강풍반경이 **300km**라면:

강풍반경 내부 → 실제 영향권
강풍반경 × 1.5 = **450km까지 접근 주의영역**

처럼 활용하는 방식이다.

따라서 같은 중심거리 400km라도:

34kt 반경 150km인 작은 태풍과
34kt 반경 350km인 큰 태풍은

**위험도를 다르게 판단한다.**

---

# 9. 강풍반경은 원형 하나가 아니다

JTWC/CMA 데이터에서는 강풍반경을 방향별로 받을 수 있다.

현재 파싱 구조는:

```text
NE  북동
SE  남동
SW  남서
NW  북서
```

각 방향의 반경을 따로 저장한다.

예:

```text
NE 280 km
SE 280 km
SW 180 km
NW 150 km
```

따라서 거점이 태풍 중심의 어느 방향에 있는지를 계산하고 **그 방향에 해당하는 강풍반경**을 사용하는 것이 기본 원칙이다.

---

# 10. 거점 위험도에 사용하는 데이터

현재 물류거점 위험도에는 크게 네 가지가 들어간다.

| 항목    | 데이터                     |
| ----- | ----------------------- |
| 태풍 영향 | 중심거리 / 최접근거리 / 강풍반경     |
| 강수    | WeatherAPI 현재 및 72시간 예보 |
| 풍속    | WeatherAPI              |
| 돌풍    | WeatherAPI              |

즉 태풍 중심이 멀더라도 거점 자체에 폭우나 강풍이 심하면 위험도를 높일 수 있고, 반대로 강한 태풍이라도 거점과 영향권이 충분히 멀다면 낮게 평가할 수 있는 구조다.

현재 위험도 출력은 사용자에게 복잡한 점수를 먼저 보여주기보다:

**🟢 낮음 / 🟡 주의 / 🔴 높음**

처럼 직관적으로 표시한다.

내부 점수와 판정 근거는 `typhoon_risk.py`가 최종 기준이며, 향후 임계값을 변경할 때도 이 파일을 **Single Source of Truth**로 삼는 것이 좋다.

---

# 11. 태풍 세기 표시

전문적인 표현만 사용하는 대신 화면에서는 쉬운 표현을 우선한다.

예:

**태풍 세기 🔴 강함**
`(중심기압 955 hPa)`

처럼 보여주는 방식이다.

최대풍속도 원본 수치를 그대로 보조 표시할 수 있다.

한국 기준 태풍 강도 체계를 적용할 경우 최대풍속을 기준으로 숫자 등급 또는 쉬운 표현을 병기한다.

핵심 원칙은:

> **일반 사용자는 쉬운 말로 판단하고, 아래에는 원본 수치를 남긴다.**

이다.

# 12. 태풍 이동경로

기본 경로는 **JMA 5일 예보 데이터**를 사용한다. JMA 원본에는 현재 위치와 미래 예상 위치, 중심기압, 풍속, 이동정보 등이 포함된다. 

화면은 현재:

```text
현재
12시간 후
1일 후
2일 후
3일 후
4일 후
5일 후
```

처럼 사용자가 쉽게 읽도록 표시한다.

원본 시간값은 그대로 유지하며 화면에서만 쉬운 표현으로 변환한다.

중요한 원칙은 **데이터가 없는 중국 상륙 예상선 등을 임의로 연장하지 않는다**는 것이다.

# 13. 19호 버전의 항공편 기능

이 19호 대시보드에서는 **대표 항공편 기능을 사용하지 않는다.**

따라서 Aviationstack / FlightAware 항공 API 호출, 항공편 수집 workflow, 항공편 카드, `flights.json` 출력은 제외한다.

# 17. 데이터 처리 흐름

현재 전체 구조는 대략:

```text
JMA ───────→ jma_typhoon.json
KMA ───────→ kma_typhoon.json
CMA ───────→ cma_typhoon.json
JTWC ──────→ jtwc_typhoon.json

WeatherAPI → weather.json

             ↓

typhoon_compare.json
typhoon_impact.json
typhoon_risk.json

             ↓

dashboard.json

             ↓

index.html
```

이다.

`index.html`은 계산을 다시 하는 곳이라기보다 **최종 dashboard.json을 사람이 보기 좋게 표시하는 화면**에 가깝다.

# 20. 대시보드 판정의 핵심 원칙

누군가 **“이 대시보드 위험도 기준이 뭐예요?”**라고 물으면 가장 짧게는 이렇게 설명하면 된다.

> **태풍 중심과 단순 거리만 보는 것이 아니라, JTWC의 실제 강풍반경을 기준으로 거점이 영향권에 들어오는지 계산하고, JMA의 5일 경로와 WeatherAPI의 현지 강수·풍속·돌풍을 함께 반영합니다. JMA와 KMA 경로 차이는 예보 불확실성 참고값으로 표시하고, CMA 정보는 중국 측 현재 태풍 상태를 참고합니다.**

이 한 문장이 현재 시스템의 핵심이야.

### README도 이제 업데이트하는 게 좋아

현재 업로드한 README는 아직 **“Step 1: JMA” 단계 문서**라서 현재 대시보드 전체 구조를 설명하기에는 많이 오래됐어. 예를 들어 MNL이 없고, CMA/JTWC/WeatherAPI 및 위험도 계산 기준도 아직 포함되어 있지 않아. 

원하면 다음에 내가 **지금 위 내용을 그대로 정리해서 기존 `README.md`를 완전히 교체할 수 있는 최신 운영 매뉴얼 버전**으로 만들어줄 수 있어. 그러면 GitHub 첫 화면에서 README 하나만 읽어도 **API 현황 → 위험도 기준 → 항공편 → 데이터 흐름 → 파일 역할**까지 전부 알 수 있게 만들면 돼.
